本文记录本项目的功能实现、从 IAR 工程切换到 arm-none-eabi-gcc 构建的过程、踩过的坑，
以及用 ST-Link + OpenOCD 烧写的完整步骤。

> **最后更新：2026-10-04**。本次更新内容：
> ① 记录实测可稳定写入的烧写命令（坑 9 / 第六节）；
> ② 记录"上电两灯全亮"的原因与修法（坑 10）；
> ③ 补充引脚低电平有效说明与上位机串口测试步骤（第七节）；
> ④ 新增 DHT11 温湿度驱动（PB12），并把上报改成**按需触发**：命令 bit3 = 1 时回发一次
>     `T=26,H=59`，平时不主动发送（第二节协议表 / 第三节 4 / 第七节）。

## 一、项目概况

| 项目 | 说明 |
|---|---|
| MCU | STM32F103C8T6（LQFP48，Flash 64K / RAM 20K） |
| 系统时钟 | HSI + PLL ×16 = 64 MHz |
| 原始工程 | STM32CubeMX 生成，工具链为 **IAR EWARM**（`EWARM/Project.eww`） |
| 当前构建 | 本机改为 **arm-none-eabi-gcc + Makefile**（本机未装 IAR） |
| 烧写方式 | ST-Link V2 + OpenOCD |
| 功能 | 上位机经 USART1 下发命令，控制红灯 / 蓝灯 / 蜂鸣器 |

### 引脚分配

| 引脚 | 功能 | 说明 |
|---|---|---|
| PA9 | USART1_TX | 串口发送 |
| PA10 | USART1_RX | 串口接收 |
| PA7 | GPIO 输出 | 红灯（**低电平有效**，拉低点亮） |
| PA6 | GPIO 输出 | 蓝灯（**低电平有效**，拉低点亮） |
| PA5 | GPIO 输出 | 蜂鸣器（**低电平有效**，拉低响） |
| PB12 | 单总线 | DHT11 温湿度数据线（DATA） |

> 上电初始状态：PA5/PA6/PA7 在 `MX_GPIO_Init()` 里被置**高**，即**两灯灭、蜂鸣器不响**。

## 二、串口通讯协议

- 串口参数：**115200 / 8 数据位 / 无校验 / 1 停止位**，无硬件流控。
- 上位机每发 **1 个字节** 就是一条命令，**只有低 4 位有效**：

| 位 | 对应外设 | 1 | 0 |
|---|---|---|---|
| bit0 | 红灯 PA7 | 点亮 | 熄灭 |
| bit1 | 蓝灯 PA6 | 点亮 | 熄灭 |
| bit2 | 蜂鸣器 PA5 | 响 | 不响 |
| bit3 | 温湿度上报 | **回发一次温湿度** | 不回发 |

> **上位机侧永远是 1=开 / 0=关**，与硬件极性无关。
> 因为板上三路输出都是**低电平有效**，固件里用 `ACTIVE()` 宏把命令位反转成引脚电平
> （命令位 = 1 → 写 `GPIO_PIN_RESET` 拉低；= 0 → 写 `GPIO_PIN_SET` 拉高）。
> 每发一个字节是**全量状态**：字节里为 0 的位对应的外设会被关掉。

示例：

| 发送值 | 效果 | 实测 |
|---|---|---|
| `0x01` | 红灯亮，其余关 | ✅ |
| `0x02` | 蓝灯亮，其余关 | ✅ |
| `0x04` | 蜂鸣器响，其余关 | ✅ |
| `0x07` | 三个全开 | — |
| `0x08` | 三路全关，并**回发一次温湿度** | ✅ |
| `0x09` | 红灯亮，并回发一次温湿度 | ✅ |
| `0x0A` | 蓝灯亮，并回发一次温湿度 | ✅ |
| `0x00` | 全部关闭，不回发 | ✅ |

**温湿度回发格式**（bit3 = 1 时，单片机读一次 DHT11 后发回一行）：

```
T=26,H=59\r\n
```

- 上位机解析：去掉结尾 `\r\n` → 按 `,` 分成两段 → 每段按 `=` 取值，转成整数即可。
- `T` 为温度（℃），`H` 为湿度（%RH），均为整数。
- 读取失败时发 `T=ERR,H=ERR\r\n`。
- **没有 bit3 触发时不会主动发任何东西**（不轮询、不定时上报）。
- DHT11 两次采样间隔需 >1s，上位机不要连续高频请求，否则会回 `T=ERR,H=ERR`。

## 三、程序结构

### 1. 串口中断收数 → 入队

`Core/Src/usart.c`

- `MX_USART1_UART_Init()`：初始化 USART1，随后调用 `HAL_UART_Receive_IT()` 开启单字节中断接收。
- `HAL_UART_RxCpltCallback()`（中断上下文）：把收到的字节写入**环形队列**，并再次挂起接收，形成循环。
- 队列为 64 字节环形缓冲区：
  - `s_rx_head` 只由中断修改，`s_rx_tail` 只由主循环修改；
  - 队满时**丢弃新字节**（不覆盖未处理数据）。
- `HAL_UART_MspInit()`：使能 USART1 时钟、配置 PA9/PA10、打开 USART1 中断。

### 2. 中断入口

`Core/Src/stm32f1xx_it.c`

```c
void USART1_IRQHandler(void)
{
  HAL_UART_IRQHandler(&huart1);
}
```

### 3. 主循环轮询 → 解析 → 执行

`Core/Src/main.c`

```c
while (1)
{
  uint8_t cmd;
  if (Usart_Queue_Pop(&cmd))   /* 队列非空才取出 */
  {
    Execute_Command(cmd);      /* 取低 4 位控制 PA7/PA6/PA5 */
  }
}
```

命令解析（注意：三路输出都是低电平有效，这里做了电平反转；bit3 触发一次温湿度回发）：

```c
/* 上位机命令位定义（数据低 4 位有效） */
#define CMD_LED_RED    0x01U   /* bit0：红灯 PA7，1 点亮 / 0 熄灭 */
#define CMD_LED_BLUE   0x02U   /* bit1：蓝灯 PA6，1 点亮 / 0 熄灭 */
#define CMD_BUZZER     0x04U   /* bit2：蜂鸣器 PA5，1 响 / 0 不响 */
#define CMD_REPORT_DHT 0x08U   /* bit3：1 = 回发一次温湿度 / 0 = 不回发 */

/* 低电平有效：命令位=1 拉低（点亮/响），=0 拉高（熄灭/不响） */
#define ACTIVE(bit)  ((bit) ? GPIO_PIN_RESET : GPIO_PIN_SET)

static void Execute_Command(uint8_t cmd)
{
  cmd &= 0x0FU;

  /* bit0~bit2：红灯 / 蓝灯 / 蜂鸣器 */
  HAL_GPIO_WritePin(GPIOA, GPIO_PIN_7, ACTIVE(cmd & CMD_LED_RED));
  HAL_GPIO_WritePin(GPIOA, GPIO_PIN_6, ACTIVE(cmd & CMD_LED_BLUE));
  HAL_GPIO_WritePin(GPIOA, GPIO_PIN_5, ACTIVE(cmd & CMD_BUZZER));

  /* bit3 为 1：读一次 DHT11 并把温湿度回发给上位机 */
  if ((cmd & CMD_REPORT_DHT) != 0U)
  {
    uint8_t temp = 0U;
    uint8_t humi = 0U;
    uint8_t ret = DHT11_Read_Data(&temp, &humi);

    Send_DHT11(ret, temp, humi);
  }
}
```

### 4. DHT11 温湿度（按需上报，PB12）

`Core/Src/dht11.c` + `Core/Inc/dht11.h`

- **只在上位机命令的 bit3 = 1 时读一次**，读完立刻把结果发回串口；
  平时**不轮询、不定时上报**，串口保持安静。
- 数据线接在 **PB12**，单总线协议：主机拉低 ≥18ms → 释放 → 从机应答 → 40 位数据（湿度整/湿小数/温度整/温小数/校验和）。
- **微秒级延时用 DWT 的 CYCCNT**（`HAL_Delay` 只能到毫秒，不够用）：
  `CoreDebug->DEMCR |= TRACEENA; DWT->CTRL |= CYCCNTENA;`，靠 32 位计数器回绕做无符号相减计微秒。
- **同一根线要切换方向**：发送时 `GPIO_MODE_OUTPUT_PP`，读取时切成 `GPIO_MODE_INPUT` + `GPIO_PULLUP`。
  内部上拉约 40k 偏弱，建议数据线外接 **4.7k~10k 上拉电阻**到 3V3。
- 回发格式（`Send_DHT11()` 手工拼字符串，因为无 newlib 不能用 `printf`）：

  ```
  T=26,H=59\r\n     读取成功（T 温度℃ / H 湿度%RH，均为整数）
  T=ERR,H=ERR\r\n   读取失败（无应答或校验和错误）
  ```

- 两次采样间隔需 >1s；上位机不要连续高频请求，否则会收到 `T=ERR,H=ERR`。

## 四、踩坑记录

### 坑 1：串口引脚配了，但外设根本没使能

现象：`pa9.cfg` 里 `PA9/PA10` 已经标成 `USART1_TX/RX`，但工程里**没有 `usart.c`**，
`stm32f1xx_hal_conf.h` 里 `HAL_UART_MODULE_ENABLED` 是**注释状态**，`.ioc` 的 IP 列表里也没有 USART1。

解决：
1. 新建 `Core/Src/usart.c` + `Core/Inc/usart.h`，手写初始化。
2. 打开 `Core/Inc/stm32f1xx_hal_conf.h` 里的 `#define HAL_UART_MODULE_ENABLED`。
3. 把 `stm32f1xx_hal_uart.c` 加进构建（IAR 是加进 `bishe.ewp`；gcc 是加进 `Makefile`）。

> 注意：`.ioc` 里 USART1 没在 IP 列表中，若以后用 CubeMX 重新生成代码，可能覆盖这些改动。
> 规范做法是在 CubeMX 里正式启用 USART1 的 Asynchronous 模式。

### 坑 2（最坑）：SWD 被固件关掉，ST-Link 连不上

现象：OpenOCD 普通连接报错

```
Info : STLINK V2J37S7 (API v2) VID:PID 0483:3748
Info : Target voltage: 3.127692
Error: init mode failed (unable to connect to the target)
```

原因：`.ioc` 中 SYS 的调试模式被设成了 **No Debug**（`VP_SYS_VS_ND`），
CubeMX 因此在 `stm32f1xx_hal_msp.c` 里生成了：

```c
__HAL_AFIO_REMAP_SWJ_DISABLE();   /* JTAG 和 SWD 一起关掉！ */
```

而 `HAL_MspInit()` 在 `HAL_Init()` 里很早就执行，所以芯片一上电就自己把 SWD 关了，
之后调试器再也连不上——只有**复位下连接**（趁固件还没跑起来）能连上。

验证方法：

```bash
# 普通连接：失败
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg -c "init; targets; exit"

# 复位下连接：成功
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg \
  -c "reset_config srst_only srst_nogate connect_assert_srst" \
  -c "init; targets; exit"
```

成功的话会看到：

```
Info : [stm32f1x.cpu] Cortex-M3 r1p1 processor detected
Info : device id = 0x20036410
Info : flash size = 64 KiB
```

解决（本工程已修改）：

```c
/* Core/Src/stm32f1xx_hal_msp.c */
// 旧：__HAL_AFIO_REMAP_SWJ_DISABLE();    ← 关掉 JTAG + SWD
__HAL_AFIO_REMAP_SWJ_NOJTAG();          /* 只关 JTAG，保留 SWD */
```

几种宏的区别：

| 宏 | 效果 |
|---|---|
| `__HAL_AFIO_REMAP_SWJ_ENABLE()` | JTAG + SWD 全开（默认） |
| `__HAL_AFIO_REMAP_SWJ_NOJTAG()` | 关 JTAG，**保留 SWD** ← 开发调试推荐 |
| `__HAL_AFIO_REMAP_SWJ_DISABLE()` | JTAG + SWD 全关 ← 会把自己锁死 |

> 若要和 CubeMX 保持同步：把 SYS 的 **Debug** 从 `No Debug` 改成 **`Serial Wire`**。

### 坑 3：Homebrew 版 arm-none-eabi-gcc 没有 newlib，`stdint.h` 找不到

现象：

```
.../include/stdint.h:11:16: fatal error: stdint.h: No such file or directory
   11 | # include_next <stdint.h>
```

原因：GCC 自带的 `stdint.h` 在“宿主环境”下会 `#include_next <stdint.h>` 去找 C 标准库的版本，
而这个 Homebrew 版工具链的依赖里**没有 newlib**（无 `libc.a` / `libm.a` / newlib 头文件）。

解决：编译时加 `-ffreestanding`。此时 `__STDC_HOSTED__ == 0`，GCC 改用自带的 `stdint-gcc.h`，不再依赖 newlib。

```bash
arm-none-eabi-gcc -c -ffreestanding ...
```

裸机固件本来就用 `-ffreestanding`，属于正常且推荐的做法。

### 坑 4：链接时缺 `__libc_init_array`、`memset` 等

没有 libc，所以：

1. CMSIS 的 GCC 启动文件会调用 `__libc_init_array`（本来由 newlib 提供）。
2. GCC 对 `RCC_OscInitTypeDef x = {0};` 这类结构体初始化会生成 `memset` 调用。

报错示例：

```
undefined reference to `memset'
(memset): Unknown destination type (ARM/Thumb)
dangerous relocation: unsupported relocation
```

解决：新建 `Core/Src/syscalls.c`，自行实现：

- `__libc_init_array()`：遍历执行 `.preinit_array` / `.init_array`。
- `memset` / `memcpy` / `memmove` / `memcmp`。

> 本项目没用到 `printf` / `malloc`，所以不需要 `_write` / `_sbrk` 等。
> 若以后要用 `printf` 重定向，建议换装带 newlib 的工具链（ARM 官方 `gcc-arm-none-eabi` 或 IAR）。

### 坑 5：IAR 的启动文件不能用于 gcc

工程里的 `EWARM/startup_stm32f103xb.s` 是 **IAR 汇编语法**，`EWARM/*.icf` 是 IAR 链接脚本，gcc 都用不了。

但 CMSIS 包里**本来就带了 GCC 版**，直接复用即可，不用自己写：

```
Drivers/CMSIS/Device/ST/STM32F1xx/Source/Templates/gcc/startup_stm32f103xb.s
```

链接脚本 CMSIS 里没有，需要自己写（见 `STM32F103C8Tx_FLASH.ld`）。

### 坑 6：zsh 不对未加引号的变量做分词（写构建/校验命令时踩到）

在 macOS 的 zsh 里，下面这种写法**不会**把变量拆成多个参数：

```zsh
INC="-ICore/Inc -IDrivers/..."
arm-none-eabi-gcc $INC ...        # 整个字符串被当成“一个”参数！
```

结果就是头文件路径没生效，报 `xxx.h: No such file or directory`。
解决：用数组，或把每个参数写全。

```zsh
# 方式一：数组
includes=(-ICore/Inc -IDrivers/CMSIS/Include)
arm-none-eabi-gcc "${includes[@]}" ...

# 方式二：直接写全
arm-none-eabi-gcc -ICore/Inc -IDrivers/CMSIS/Include ...
```

### 坑 8：烧写时 `timeout waiting for algorithm` / `Unable to reset target`

现象一：连接能成功（能看到 Cortex-M3、`device id`、`flash size`），但一写 Flash 就失败：

```
Warn : Adding extra erase range, 0x0800155c .. 0x080017ff
Error: timeout waiting for algorithm, a target reset is recommended
Error: flash write failed just before address 0x8000000
```

现象二：用一次性 `program` 命令时：

```
Error: timed out while waiting for target halted
in procedure 'program'
Error: ** Unable to reset target **
```

原因与解决：

1. **SWD 速度太高**。默认 1000 kHz，飞线稍长或接触稍差，传输烧写算法时就会超时。
   本例实测：1000 kHz / 480 kHz 都失败，**降到 100 kHz 成功率最高**。
   ```bash
   -c "adapter speed 100"
   ```
   即使降到 100 kHz，仍**偶发**失败（报 `timeout waiting for algorithm` / `failed to get read pointer` /
   `jtag status contains invalid mode value`）。**直接重跑同一条命令即可**——本例第二次重试就
   `wrote 5484 bytes` / `verified 5484 bytes` 成功。见坑 9。
2. **别用一次性 `program`**。它内部会调 `reset`，而如果 ST-Link 的 NRST 没有接到板子的 NRST，
   就会报 `Unable to reset target`。改成“分步执行、自己控制”更稳：
   ```bash
   -c "init" -c "halt" \
   -c "stm32f1x mass_erase 0" \
   -c "flash write_image erase build/bishe.hex" \
   -c "verify_image build/bishe.hex"
   ```
3. `connect_assert_srst` 本身也有偶发性：同样的命令可能这次成功、下次失败（报
   `init mode failed (unable to connect to the target)`）。
   遇到时先检查飞线是否松动、重试；实在连不上可把 **BOOT0 拉高**（从系统存储器启动），
   此时固件不运行，SWD 一定可用。

### 坑 9：烧写"时好时坏"，同一命令要重试（本项目最终确认可用的做法）

飞线环境下，**同样的命令不同次执行结果可能不同**，这不是代码问题。2026-10-04 刷新固件时
连续跑了 3 次同一命令：

| 第几次 | 结果 |
|---|---|
| 第 1 次 | `mass erase complete` 后 `failed to get read pointer` / `jtag status contains invalid mode value - communication failure` / `error waiting for target flash write algorithm` → **失败** |
| 第 2 次 | `wrote 5484 bytes` / `verified 5484 bytes` → **成功** |
| 第 3 次 | 同样成功 |

**结论**：命令写对之后，**失败就原样重跑**，一般 2~3 次内必成。批量写脚本时建议套一个
`for i in 1 2 3` 循环，成功即跳出。

### 坑 10：一上电两盏灯全亮（输出是低电平有效）

现象：烧进去后**上电两盏灯就亮**，不用发命令。

原因：板上的红灯/蓝灯/蜂鸣器接法是**低电平有效**——引脚输出低电平时导通点亮/发声。
而 CubeMX 生成的 `gpio.c` 默认把输出脚初始化为 `GPIO_PIN_RESET`（低），于是上电即亮。

解决（两处一起改，缺一不可）：

1. `Core/Src/gpio.c` 的 `MX_GPIO_Init()` 里，把 PA5/PA6/PA7 的初始电平改成**高**：

   ```c
   /*Configure GPIO pin Output Level (PA5/PA6/PA7 低电平有效，初始置高=全灭/不响) */
   HAL_GPIO_WritePin(GPIOA, GPIO_PIN_5|GPIO_PIN_6|GPIO_PIN_7, GPIO_PIN_SET);
   ```

2. `Core/Src/main.c` 的 `Execute_Command()` 里把 SET/RESET 反转（用 `ACTIVE()` 宏，见第三节）。

> 若只改 1 不改 2：初始是灭的，但命令逻辑反了（发 0x01 反而熄灭）。
> 若只改 2 不改 1：命令逻辑对，但上电瞬间仍然是亮的。

### 坑 11：蜂鸣器接了 GND 和 IO、却一直不响

现象：蜂鸣器模块的 `GND` 接到板子 GND、`IO` 接到 PA5，发 `0x04` 也不响。

原因：**3 脚蜂鸣器模块（VCC / GND / IO）的 `VCC` 忘了接 3V3**。
模块内部的三极管没有供电，无论如何都不会响；只有 GND 和 IO 是不够的。

排查顺序：

1. 先确认发的是带 bit2 的命令（`0x04`）；`0x00/0x01/0x02/0x08` 都不会响。
2. 量 PA5：发 `0x04` 应为低（0V），发 `0x00` 应为高（3.3V）。灯能用说明固件这一路没问题。
3. 检查模块 **VCC 是否接 3V3**（最容易漏）。
4. 若仍不响，把蜂鸣器直接接 3V3 / GND 试：
   - 立刻响 → 有源蜂鸣器，注意触发极性（本工程按**低电平有效**写，接法应为 `+ → 3V3`、`− → PA5`）；
   - 只轻微"嗒"一声 → **无源蜂鸣器**，需要 2~4kHz 方波，静态电平不会响，得改代码做软件翻转或 PWM。

## 五、构建教程（arm-none-eabi-gcc）

### 环境

| 组件 | 版本 / 路径 |

```bash
# 前 2 个字应该是：初始栈指针 0x20005000、复位向量（带 thumb 位）

# 期望：0050 0020 dd19 0008   （SP=0x20005000，Reset_Handler=0x080019DD）
```

> 复位向量会随代码变化，只要**第 1 个字是 `0050 0020`**（栈顶 0x20005000）即链接正常。

## 六、烧写教程（ST-Link + OpenOCD）

### 连接

ST-Link 与开发板至少接 4 根线：`SWCLK` / `SWDIO` / `GND` / `3V3`。
插上 USB 后可用 `openocd ... -c "init; targets; exit"` 确认能否识别。

### 第一次烧写（复位下连接 + 降速到 100kHz）

片子里旧固件把 SWD 关了，第一次要用 `connect_assert_srst` 让芯片停在复位状态再连；
同时**必须把 SWD 速度降到 100 kHz**，否则写 Flash 会 `timeout waiting for algorithm`：

```bash
cd /Users/CiCi/stm32demo/bishe
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg \
  -c "adapter speed 100" \
  -c "reset_config srst_only srst_nogate connect_assert_srst" \
  -c "init" -c "halt" \
  -c "stm32f1x mass_erase 0" \
  -c "flash write_image erase build/bishe.hex" \
  -c "verify_image build/bishe.hex" \
  -c "reset run" -c "exit"
```

成功时的关键输出：

```
stm32x mass erase complete
wrote 6800 bytes from file build/bishe.hex in 1.281800s (4.178 KiB/s)
verified 6800 bytes in 0.291548s (18.369 KiB/s)
```

> 不建议用一次性 `program ... reset exit`：它内部会调 `reset`，NRST 没接好时会报
> `Unable to reset target`（详见坑 8）。

### 本工程推荐烧写方式（2026-10-04 实测可用）

一次成功的标准命令：

```bash
cd /Users/CiCi/stm32demo/bishe
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg \
  -c "adapter speed 100" \
  -c "reset_config srst_only srst_nogate connect_assert_srst" \
  -c "init" -c "halt" \
  -c "stm32f1x mass_erase 0" \
  -c "flash write_image erase build/bishe.hex" \
  -c "verify_image build/bishe.hex" \
  -c "reset run" -c "exit"
```

判断成功的唯一标准：输出里出现

```
wrote 6800 bytes from file build/bishe.hex ...
verified 6800 bytes ...
```

**失败就原样重跑**（详见坑 9）。要省事可以用循环，成功即跳出：

```bash
cd /Users/CiCi/stm32demo/bishe
for i in 1 2 3 4 5; do
  echo "=== 第 $i 次 ==="
  out=$(openocd -f interface/stlink.cfg -f target/stm32f1x.cfg \
    -c "adapter speed 100" \
    -c "reset_config srst_only srst_nogate connect_assert_srst" \
    -c "init" -c "halt" \
    -c "stm32f1x mass_erase 0" \
    -c "flash write_image erase build/bishe.hex" \
    -c "verify_image build/bishe.hex" \
    -c "reset run" -c "exit" 2>&1)
  echo "$out" | grep -E "wrote|verified|Error"
  echo "$out" | grep -q "verified 6800 bytes" && { echo "✅ 成功"; break; }
done
```

> 各 `-c` 的含义：
> `adapter speed 100` 降速（必须）→ `connect_assert_srst` 复位下连接（旧固件关过 SWD 时必需）
> → `init; halt` 连上并停住 → `mass_erase 0` 整片擦除 → `flash write_image erase` 写入
> → `verify_image` 回读校验 → `reset run` 复位运行。
>
> 注意：**不要用 `-c "reset halt"` 代替 `-c "halt"`**，实测会报 `timed out while waiting for target halted`。

### 验证板子真的在跑

不给复位信号时，可用“同一会话内 resume 前后对比 PC”判断程序是否在正常执行：

```bash
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg \
  -c "adapter speed 100" -c "init" -c "halt" -c "reg pc" \
  -c "resume" -c "sleep 300" -c "halt" -c "reg pc" -c "exit"
```

两次 PC 不同即说明 CPU 在运行。若 PC 停在 `0xFFFFFFFE` 且模式是 `Handler HardFault`，
说明程序跑飞了。

### 烧 `.bin` 的写法

`.bin` 没有地址信息，需要手动指定起始地址（同样建议分步 + 重试）：

```bash
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg \
  -c "adapter speed 100" \
  -c "reset_config srst_only srst_nogate connect_assert_srst" \
  -c "init" -c "halt" \
  -c "stm32f1x mass_erase 0" \
  -c "flash write_image erase build/bishe.bin 0x08000000" \
  -c "reset run" -c "exit"
```

### 常用参数说明

| 参数 | 含义 |
|---|---|
| `-f interface/stlink.cfg` | 使用 ST-Link 调试器（自动选 SWD 传输） |
| `-f target/stm32f1x.cfg` | 目标芯片为 STM32F1 系列 |
| `adapter speed 100` | 把 SWD 时钟降到 100 kHz，飞线不稳时必用（见坑 8） |
| `connect_assert_srst` | 连接前先按住复位，绕过被固件关掉的 SWD |
| `init; halt` | 连接并停住内核（分步写法的起点） |
| `flash write_image erase <file>` | 擦除并写入固件 |
| `verify_image <file>` | 回读校验 |
| `reset run` / `resume` | 复位运行 / 继续运行 |
| `program <file> verify reset exit` | 一体化命令（内部会 reset，NRST 没接好会失败） |

## 七、上位机发送 / 接收测试（macOS）

板子跑起来后，在 Mac 上用 USB-TTL（本机是 `/dev/cu.usbserial-110`）发字节即可验证；
命令里带 bit3 时板子会**回发温湿度**，所以接收线（PA9 → USB-TTL 的 RX）也要接上。

### 接线

| USB-TTL | 开发板 |
|---|---|
| TX | PA10（USART1_RX） |
| RX | PA9（USART1_TX，**要收温湿度就必须接**） |
| GND | GND（**必须共地**） |
| 3V3 | 3V3（若开发板已单独供电则不接） |

### 找到串口设备

```bash
ls -1 /dev/cu.*
# 常见：/dev/cu.usbserial-110（CH340/CP210x 类 USB-TTL）
```

### 发送一个字节

macOS 没有方便的 `echo > /dev/tty` 用法（波特率会不对），推荐**在同一个进程里**先 `stty` 配好参数、再写端口：

```bash
# 发送 0x01（红灯亮）；\001 是八进制，等于 0x01
exec 3<>/dev/cu.usbserial-110
stty -f /dev/cu.usbserial-110 115200 cs8 -cstopb -parenb -icanon -echo
sleep 0.3
printf '\001' >&3
sleep 0.3
exec 3>&-
```

把 `\001` 换成对应八进制值即可：

| 想要 | 发送值 | printf 写法 |
|---|---|---|
| 红灯亮 | `0x01` | `printf '\001' >&3` |
| 蓝灯亮（红灯灭） | `0x02` | `printf '\002' >&3` |
| 蜂鸣器响 | `0x04` | `printf '\004' >&3` |
| 全部关闭 | `0x00` | `printf '\000' >&3` |
| 只请求温湿度（三路全关） | `0x08` | `printf '\010' >&3` |
| 红灯亮 + 请求温湿度 | `0x09` | `printf '\011' >&3` |
| 蓝灯亮 + 请求温湿度 | `0x0A` | `printf '\012' >&3` |

> 要点：**必须用同一个文件描述符（如 `3<>`）打开并写**，不要 `stty` 之后再 `>` 重开一次端口，
> 否则波特率设置可能失效导致收到乱码。

### 收发一体：发命令并读回温湿度

把接收端 `cat` 挂到同一个文件描述符上，发完命令就能看到板子回发的 `T=..,H=..`：

```bash
exec 3<>/dev/cu.usbserial-110
stty -f /dev/cu.usbserial-110 115200 cs8 -cstopb -parenb -icanon -echo

cat <&3 &                 # 后台接收并打印（前台会一直挂着，收完用 kill 结束）
sleep 0.3
printf '\010' >&3         # 发 0x08：只请求温湿度，不点灯
sleep 0.6
kill %1 2>/dev/null       # 结束 cat
exec 3>&-
```

期望输出一行：`DHT11 init ok` 之后每次发 `0x08` 会多出一行 `T=26,H=59`。

### 实测结果（2026-10-04）

| 步骤 | 发送 | 现象 | 结论 |
|---|---|---|---|
| 1 | `0x01` | 红灯亮 | ✅ |
| 2 | `0x02` | 红灯灭、蓝灯亮 | ✅ |
| 3 | `0x00` | 全灭 | ✅ |
| 4 | 静默 4s（不发任何命令） | 串口**无任何输出** | ✅ |
| 5 | `0x08` | 三路全关 + 回发 `T=26,H=59` | ✅ |
| 6 | `0x0A` | 蓝灯亮 + 回发 `T=26,H=59` | ✅ |
| 7 | `0x02`（不带 bit3） | 蓝灯亮，**不回发** | ✅ |
| 8 | `0x00`（不带 bit3） | 全灭，**不回发** | ✅ |

功能链路（中断收数 → 入队 → 主循环轮询解析 → 控制 PA7/PA6/PA5 + 按 bit3 回发 DHT11）验证通过。

## 九、遗留事项 / 后续建议

1. **CubeMX 重新生成代码的风险**
   - `.ioc` 的 IP 列表里没有 USART1，重新生成可能覆盖 `usart.c` 相关改动。
   - SYS 的 Debug 仍是 `No Debug`，重新生成会让 SWD 又被关掉。
   - `gpio.c` 里 PA5/PA6/PA7 的初始电平也是手改的，重新生成会被改回 `GPIO_PIN_RESET`
     （于是上电又全亮，见坑 10）；PB12（DHT11 数据线）的初始化同样在 `gpio.c` 里手工加的。
   - 建议在 CubeMX 里：启用 USART1 Asynchronous，并把 SYS Debug 改成 `Serial Wire`；
     引脚初始电平也在 CubeMX 的 GPIO 配置里设为 High，并把 PB12 配成开漏/输入输出可切换的 GPIO。

2. **没有 newlib**
   - 目前不用 `printf` 所以没问题（串口回发是手工拼字符串 + `HAL_UART_Transmit`）。
     若后续需要 `printf`，建议换装 ARM 官方工具链或 IAR。

3. **串口协议**
   - 现在是“一字节即一条命令、无校验”。若担心干扰或丢包，
     可改成带帧头/帧尾（或长度+校验）的帧协议，队列按帧存储。
   - 温湿度回发是**被动触发**（bit3 = 1 才发），不会定时打扰上位机；
     但两次采样需间隔 >1s，上位机不要连续高频请求。

4. **已完成 / 已验证**
   - 红灯、蓝灯、蜂鸣器均经串口实测通过（蜂鸣器为 3 脚模块，注意接 VCC，见坑 11）。
   - DHT11（PB12）读取实测通过，回发格式 `T=26,H=59`。
   - 按需上报实测通过：静默时串口无输出；发 `0x08` / `0x0A` 回发温湿度；不带 bit3 时不回发。
   - 烧写流程（`adapter speed 100` + 分步 + 重试）实测可稳定写入。
